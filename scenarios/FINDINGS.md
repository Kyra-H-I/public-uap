# Findings register

Strain discovered by scenario walks, live host experience, or external protocol
review lands here — **never directly in the specification**. Two different bars
apply: a **new primitive** is promoted into spec work only when several sources
make the same case from unrelated directions; a **demonstrated internal
contradiction** (two normative statements that cannot both hold) is a bug, may
be corrected on a single source, and gets a register row recording the
correction so the closed door keeps its reasoning. Rejected findings stay
listed for the same reason.

Statuses: **open** (evidence accumulating) · **promoted** (accepted as spec
work, target named) · **rejected** (with reasoning) · **absorbed** (already
covered by a named known gap).

| Id | Finding | Evidence | Status |
|---|---|---|---|
| F-001 | **Cross-turn command lifecycle.** Events carry no command identity, progress, or terminal result, so work that outlives its turn can never resolve its command's ending. | Long-running walk (defining case); automotive preconditioning; live host experience with unresolved navigation acceptances. Three unrelated sources. | **Promoted** — pre-1.0 wire-binding milestone, alongside emitted-envelope schemas and undo redemption. Shape is deliberately minimal: `command_id` + optional progress + terminal result on events, feeding the existing accepted-resolution machinery. |
| F-002 | **Evidence attestation layer.** `completed` cannot state how far its evidence reaches (hub state vs device ack vs physical outcome; app streaming vs platform accepted vs viewers receiving). | Smart-home walk; live-media half of the long-running walk. Two domains — one short of comfortable. | **Open.** Deliberately not promoted; a print/scan-queue scenario is the planned third look. If promoted, the shape is a declaration on evidence, never a device ontology. |
| F-003 | **Cross-provider data plane.** No mechanism for an artifact to cross provider boundaries with provenance, consent readability, and fidelity. | Cross-provider walk (defining case); email walk's attachment boundary. Already named as known gap #6. | **Absorbed / design-gated.** Requirements are mapped in the cross-provider walk; design is deliberately deferred until live usage shows which crossings actually fail which axes. Consent/audit story before transport. |
| F-004 | **Provider identity is not binding identity.** Two live windows/tabs of one application collide on one provider id; `ambiguous` covers rival providers, not twin sessions. | Browser walk; live field experience with two desktop editor windows. Two unrelated sources. | **Promoted + specified (semantic invariant)**: §1, *Provider identity is not binding identity* — `provider` stays the stable application identity; a *binding* is one live session, discriminated at transport level; route by binding, grant independently of binding (within the host's authority context). The **wire representation** of the binding discriminator is deliberately pending the wire-binding milestone — this draft names no bytes for it, so do not look for them; open with it: whether one transport connection may announce several bindings. The discriminator is provider-asserted — forging it (two windows as one binding, or one as two) collapses into the spec's coherent-liar trust boundary, not into anything this wire detects. Reference implementation in progress. |
| F-005 | **Binding lifecycle on provider death.** A provider vanishing mid-binding (page navigation, app crash, restart with handles outstanding) has no specified sequence: in-flight command resolution, terminal notice, what a reappearing provider may claim. | Browser walk. One source. | **Open.** The application-restart-while-handles-exist case in other domains is the natural second look. |
| F-006 | **Browser must not shadow native providers** — proposed core rule that a mediating provider refuse origins publishing their own UAP endpoint. | Browser walk (raised and examined). | **Rejected.** Route preference is host policy, already assurance-driven per operation; freezing it into the core would forbid legitimate mixed compositions on one origin. Recorded so it is not re-litigated from scratch. |
| F-007 | **Provider implementation/build identity.** Assurance is version-specific, but nothing identifies the exact implementation build a conformance result tested — provider id alone cannot tell a host whether the bound implementation is the one that earned the evidence. The layer between provider and binding: `provider → implementation/build → binding → targets`. | Consolidated external review; implied by the assurance model's own "descriptive, version-specific" claim; security review added the grant dimension. | **Open — design.** The semantic distinction is accepted; the wire representation (version, build, digest) deliberately waits for the wire-binding milestone rather than being frozen ahead of it. Do not overload `provider`. **The gap has a second, sharper consequence than assurance staleness: grants attach to the provider id, so a later build under the same id — including a compromised update — silently inherits every standing grant; re-consent cannot currently be triggered by a build change because the build is invisible.** |
| F-008 | **`command_id` scope and durability.** Unique within what — binding, provider, host/provider pair? How long must idempotency history survive, and can a replacement binding resolve (or safely re-present) a command issued through a dead binding? Two bindings must not collide on `command_id = 47` merely because the provider id matches; yet a consequential command dispatched just before binding death must not run twice on reconnect-and-retry. | Consolidated external review; intersects F-001 (cross-turn lifecycle) and F-005 (binding death). | **Open — design.** Must be resolved together with F-001/F-005 in the wire-binding milestone, not improvised in transport code. |
| F-009 | **`failed` conflates execution failure with epistemic uncertainty.** An export can begin, fail at the encoder, and leave a *known* terminal state — that is failure with knowledge, not unknown outcome. "What happened" and "how much do we know about what happened" are separate dimensions. | Consolidated external review; the long-running walk's partial-write case brushes it. The bundle already disagrees with itself: the authoring skill's contract reference defines `FAILED` as "started, did not finish — state may be partial" — the execution-failure reading — while §5 says "outcome is unknown". | **Open.** Direction: keep `rejected` = never began; move `failed` toward "execution began or was attempted and did not reach the declared successful condition", with known/unknown post-state, partial effects, and evidence reported separately. §5's current sentence is under review; no new top-level status unless scenarios prove one necessary. |
| F-010 | **Consequential stale-reference retry.** The blanket "stale ref → re-resolve by identity → retry once, silently" is right for reads and wrong for send/delete/unlock/pay: a re-resolved target may no longer be covered by the consent the user actually gave. | Consolidated external review; no live incident yet. | **Open.** Direction: automatic re-resolve-and-retry only when the host can establish that target identity, preconditions, and the *scope of existing consent* remain valid; otherwise re-observe and surface. Note: the reference host currently implements the unconditional retry-once (excluding conflict/confirmed/failed) — implementation follow-up needed when this lands. |
| F-011 | **Host conformance profile.** Several load-bearing safety properties are host obligations (never treat declarations as authorization; accepted ≠ completed; never claim more than evidence; preserve binding/ref scoping; honor conflicts; no assurance upgrades on provider say-so) — two hosts can both claim "UAP support" with radically different guarantees. | Consolidated external review. | **Open — design.** Behavioural invariants only, never UI/wording. "What is a UAP-conforming host" must be answered before 1.0; likely a conformance track parallel to the provider suite. |
| F-012 | **First domain profile experiment.** Core-only interoperability stops at the envelope (`mail.send` vs `message.dispatch`). Profiles must be *extracted*, not designed: pick one tiny domain (messaging or documents), author two independent providers, and derive the smallest shared vocabulary both naturally needed. | Consolidated external review; domain-profiles positioning section. | **Open — milestone.** Semantic agreement, never capability parity; providers keep vendor capabilities beside the profile. Feeds the independent-implementations 1.0 gate. |
| F-013 | **`bound ⊆ public` withdrawn** (correction record, not an open finding). The invariant contradicted curation on its own page: "keep two hundred behind authentication" made all two hundred "drift or a dishonest provider" at bind. Resolution: the catalog is a curated pre-binding projection; the bound manifest is authoritative; dishonesty is soundness-scoped (advertising what no configuration can provide) and policed by review/registry, not wire checks. What the invariant appeared to defend was illusory for hosts — a host was never allowed to derive policy from the catalog, and per-action consent derives from bound declarations. | Consolidated external review found the contradiction; security review confirmed the lost defense was illusory. | **Closed — corrected in §1.** Reference cleanup (the never-called `exceeds()` helper, its tests, parity-copy comments) rides the same change. |

## Standing observations (not findings)

- **Structured partial failure** keeps accumulating want (smart-home group
  actions; interrupted execution) but is already inside the declared
  transactions gap — tracked there, not here.
- **The effect model's adequacy** for consent (volume-down vs door-unlock)
  has survived both walks that attacked it, *on paper*, without
  provider-specific host branches — the simulated automotive provider is
  where that claim gets falsified or confirmed with running code. No new
  policy enum is justified by current evidence.
